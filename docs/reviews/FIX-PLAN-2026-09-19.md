# Core fix implementation plan

Status: proposed implementation; no runtime fixes applied by this plan.

Basis: [review and reproductions](REVIEW-2026-09-19.md), revision `e620fff` and the reviewed working tree. Recheck the working-tree diff before implementation and preserve unrelated user edits.

## Objectives and boundaries

Fix all seven review findings through the framework's shared lifecycle, semantic indexing, adapter and test contracts. Gmail, future source adapters and Hermes must receive the same guarantees.

Required invariants:

1. An empty archive starts successfully and accepts its first indexed record without restart.
2. Every registered embedding model retains its own unfinished obligations until completion or valid cancellation.
3. Index publication, completion markers and retry acknowledgment agree; metadata alone cannot prove publication.
4. A successful close means no owned request, initializer or worker can subsequently use released resources.
5. A new process cannot acquire ownership while an old writer is still running.
6. A source signal is acknowledged only after every required feed successfully commits a complete, caught-up page.
7. Tests observe the first successful prefetch packet without changing production suppression behavior.

Preserve existing tool names, request formats, source identities, immutable record revisions, evidence IDs, canonical deletion rules and default-profile behavior. No Hermes patch or Gmail-specific workaround is required for these fixes. Internal database migration is allowed; public behavior changes are corrections to the existing contract.

## Implementation order

| Stage | Work | Why this order |
|---|---|---|
| 1 | Regression reproductions and R7 test repair | Establish a reliable, deterministic validation gate. |
| 2 | R1 sequence initialization | Fix fresh startup and establish a valid revision clock for migration. |
| 3 | R2 durable model-specific work and migration | Establish correct completion/acknowledgment semantics. |
| 4 | R3 atomic in-memory publication | Integrate accelerator failures with the corrected work lifecycle. |
| 5 | R5 initializer ownership, then R4 dependency-aware teardown | Make engine close trustworthy before the application relies on it. |
| 6 | R6 source completion contract | Correct shared adapter scheduling and signal acknowledgment. |
| 7 | Cross-boundary tests, documentation and release validation | Prove the fixes work together and remain compatible. |

Each stage should be a reviewable commit when implementation is authorized. Do not mix unrelated throughput refactors into these correctness changes.

## 1. Repair prefetch validation and test isolation — R7

Files: `tests/test_memory.py`, `tests/test_retrieval.py`; relevant shared test fixtures if needed.

### Design

- Extend `await_prefetch` to accept an optional already-observed result. Use an explicit sentinel for “no result supplied”: an empty string is a real suppressed result.
- Classify that initial value before calling the provider again. If it is the requested state, return it immediately.
- Update all four affected tests: default explicit lookup, fast lookup reuse, filtered/limited reuse, and eventual nonblocking retrieval.
- Keep the first-call latency assertion separate from waiting for eventual completion.
- Use a gated fake search and threading events to exercise immediate and delayed responses deterministically. Keep a genuine model-latency smoke separate from deterministic contract tests.
- Explicitly enable semantic initialization inside the mocked concurrency test with a scoped environment patch; restore the previous environment even on failure.
- Retain the actual pinned Hermes provider contract. Do not replace it with the untracked stub.

### Tests and acceptance

- Immediate packet is consumed once; the next identical prefetch is suppressed.
- Pending response transitions to a packet after the controlled search completes.
- Failure, freshness failure, suppression and pending are classified distinctly.
- Bare balanced search still performs a new lookup; equivalent fast search reuses the cache.
- Larger limits or source/time/entity filters do not reuse an insufficient cached response.
- The concurrency test constructs one engine with the outer semantic kill-switch both set and unset.
- Environment restoration works on both success and injected assertion failure.
- No new 90-second waits in deterministic fixtures and no weakened production assertions.

## 2. Establish sequence initialization as a schema invariant — R1

Files: `personal_memory/semantic.py`, semantic migration/startup tests.

### Design

- Ensure the semantic revision singleton exists whenever queue schema setup completes, even if there are no records or queued signals.
- Start a new archive at zero. During upgrades, never lower an existing sequence: initialize/repair it against the highest durable revision in the applicable work/history/progress tables.
- Make creation and migration transactional and idempotent. Handle the legacy queue shape before creating indexes that reference new columns.
- Audit `ensure_schema` transaction ownership: avoid accidentally committing a caller's transaction through `executescript`.
- `_activate` may then rely on the invariant. Do not hide a missing schema row by treating arbitrary initialization failures as empty work.
- Keep existing dependency/model-load failure handling separate; this fix must remove the empty-archive failure rather than repeatedly retry a broken constructor.

### Tests and acceptance

- Empty `Store` → `SemanticIndex` succeeds with zero pending work.
- Service warm-up on an empty store succeeds; ingest and retrieve a first record without restarting.
- Reopen an empty store repeatedly without incrementing revisions unnecessarily.
- Migrate an empty legacy queue and a populated legacy queue.
- Repair a missing singleton with existing revisions; the next revision is strictly newer.
- Inject migration failure and confirm rollback/retry leaves no half-migrated schema.

## 3. Persist indexing obligations per model — R2

Files: `personal_memory/semantic.py`; callers of `semantic.enqueue` in canonical ingestion/lifecycle remain source-neutral.

### Chosen design

Keep the canonical desired-state inbox and add durable model-specific indexing work. A shared queue row is a signal to distribute work, not proof that every model completed it.

Suggested internal schema:

```text
semantic_models
  model PRIMARY KEY
  registration/migration metadata

semantic_model_work
  PRIMARY KEY(model, record_id)
  seq, attempts, available_at, updated_at
  due-work index beginning with model

semantic_work
  existing shared desired-state inbox and global retirement obligations

vector_chunks / vector_done / vector_failures
  remain model-specific derived state
```

Exact migration names may follow the repository's conventions; the ownership and acknowledgment rules below are mandatory.

### Signal distribution and processing

1. Canonical writers continue to call `enqueue` inside their existing transaction. Newer signals coalesce by record and carry a monotonically increasing revision.
2. Before normal indexing, the owning worker distributes a bounded batch of shared index signals to all registered models in one transaction. Upsert each model's desired work without duplicating work for a durably complete immutable record.
3. Delete the shared signal only after its model obligations are durable, guarded by the exact revision. If no model is registered, retain the signal until activation can establish coverage.
4. The active model consumes only its own due work. Failure/backoff for A must neither postpone B nor be erased by B's success.
5. Record completion and acknowledge the matching model revision only after durable vectors, running-index publication and a final canonical visibility/revision check succeed.
6. A stale attempt must not remove or mark complete a newer revision. If canonical retirement/restoration overtook the attempt, leave the current obligation for its own pass.
7. Switching to a previously registered model loads its durable vectors and resumes its durable unfinished work. Activation is not a completion watermark.

### Retirement and restoration

- Retirements remain global: they remove vector state across model revisions, not just the active model.
- In the same retirement transaction, cancel superseded model obligations and remove obsolete completion/failure markers. Guard global acknowledgment by revision.
- Serialize visibility checks, revision comparisons and completion writes under the canonical transaction boundaries. An embed call outside the transaction may finish after retirement, but it must not resurrect evidence or discharge newer work.
- A newer restoration signal survives a concurrent retirement attempt and creates fresh per-model obligations.
- Keep canonical recall filtering as the final boundary while derived cleanup is pending.

### Registration, migration and retention

- Register a new model and perform an idempotent canonical reconciliation before declaring activation complete. If the scan is paged for large archives, persist its cursor and mark registration incomplete until finished.
- Signals arriving during registration must still be represented by the shared inbox or registered model work; use canonical write serialization and explicit registration state to prevent a handoff gap.
- Upgrade existing model keys from existing progress/bootstrap/vector metadata. Run a **one-time reconciliation for each known model**, because the old watermark may already claim progress for work that was never completed.
- Preserve valid vectors; enqueue only missing live completion obligations and required cleanup. Do not require re-embedding the whole archive.
- Do not use bounded change-history retention as the sole durability mechanism. Legacy history/progress can remain for compatibility/diagnostics, but pruning them must not erase model obligations.
- Do not silently discard inactive model backlog. If model retirement is later needed, make it explicit and make re-registration reconcile canonically.
- Keep idle polling bounded by due work, not archive size. Fan-out cost is proportional to registered model revisions; measure it with multiple revisions and document retained-state growth.

### Readiness

- `pending_records` must include the active model's unfinished publication/retry work, not merely records lacking `vector_done` in a shared queue.
- Include undistributed shared work and incomplete registration in readiness accounting; avoid double counting by record/revision.
- A constructor or accelerator failure cannot leave readiness true while required publication is absent.
- Preserve existing status fields; any new diagnostics should be additive.

### Tests and acceptance

- A→B→A with A never synced, partially synced, failed and backed off.
- B consumes shared work; A still retains its own obligation and eventually returns the record as a candidate.
- A's failure does not cause B to re-embed valid vectors or inherit its backoff.
- Crash before/after distribution, vector persistence, publication and acknowledgment.
- New signal arrives during embedding; old acknowledgment cannot delete it.
- Retire during embedding, retire then restore, restore during retirement, and duplicate ingestion.
- Registration races with ingestion and retirement; interrupted registration resumes safely.
- Migrate the exact already-broken state from the review: A absent, B complete, history/queue empty.
- History pruning and repeated reopen do not lose work or require a full archive scan each time.
- Validate candidate retrieval, readiness and embedding-call counts, not only database row counts.

## 4. Make accelerator publication failure-safe — R3

Files: `personal_memory/semantic.py`, publication/state tests.

### Design

- Build and initialize a new accelerator instance locally; assign it to `self.index` only when initialization succeeds.
- Under the index lock, validate a chunk, insert it into the accelerator, then publish its `rows` bookkeeping. The exact-vector path must update its vector and row maps consistently as well.
- Treat a backend insertion exception as ambiguous: an accelerator may mutate and then throw. Do not simply retry into an assumed-clean object.
- Mark the running accelerator unhealthy on ambiguous mutation and rebuild from valid durable chunks into a separate instance. Swap the replacement and its maps atomically once complete.
- Keep rebuild work bounded in scheduling frequency: retry/backoff rather than rebuilding on every request. If rebuilding fails, retain pending work, expose degraded readiness and let canonical keyword retrieval continue.
- Rehydrate only live/visible canonical records for rebuild; serialize the final swap against retirement so a rebuild cannot reintroduce retired labels.
- Reuse stored vectors; a publication-only failure must not call the embedding provider again.
- Integrate final completion/acknowledgment with R2's model-specific revision guard.

### Tests and acceptance

- Fail before insertion and after a simulated partial insertion.
- Fail initial accelerator setup and capacity resize.
- Fail one chunk midway through a multi-chunk record.
- Retry or rebuild returns the record without restart, duplicates or extra embedding calls.
- Rebuild races with retirement and restoration.
- Failed rebuild remains retryable and cannot report ready.
- Exercise exact-vector fallback; run an additional real-HNSW integration check when installed.

## 5. Own semantic initialization until it stops — R5

Files: `personal_memory/retrieval.py`, index-ownership/shutdown tests.

### Chosen design

Use a synchronized retrieval lifecycle with `running`, `closing` and `closed` states. Treat initialization as owned work alongside index workers. Retain the indexing lease until all such work has stopped. This is the smallest robust correction; splitting third-party model loading into a cancellable subsystem is not required.

### Implementation

- Register initialization under a lifecycle lock before entering the constructor. Reject new initialization/search submission once closing begins.
- Track active initializations explicitly, including warm-up and request-triggered initialization; do not rely only on the warm-up thread reference.
- After construction, recheck lifecycle state before publishing the engine or starting an indexing thread. Discard/close the unused engine if shutdown began.
- Coordinate worker registration/start with close so no worker can appear after the close routine decides the set is drained.
- Set stop and prohibit new work before joining. Use a shared shutdown deadline for owned work and retain references on timeout.
- If a constructor or writer outlives the budget, raise an incomplete-close error and retain the lease. A later close retries safely.
- Release the lease only after initializers, query users of the index and indexing writers have drained. Do not hold the lifecycle mutex while waiting for threads that need it to finish.
- Make repeated successful close idempotent; starting warm-up after close must not reopen resources.

### Tests and acceptance

- Gate construction before queue activation; close times out and a second owner is rejected.
- Release the gate; no new worker is published during closing; a repeated close succeeds.
- A second owner can acquire the lease only after the first has fully drained.
- Concurrent warm-up/search/close constructs at most one engine and has no registration race.
- Inject constructor failure during closing and verify cleanup still completes.
- Capture database writes in the old owner and prove none occur after lease transfer.

## 6. Make application teardown dependency-aware — R4

Files: `personal_memory/asgi.py`, `personal_memory/service.py`; review `source_runtime.py`, `workflows.py` and `investigate.py` close contracts as part of this boundary.

### Ownership order

```text
Stop accepting new application requests
  → drain already accepted request handlers
  → stop/join service workers and retrieval users
  → close retrieval/index ownership (including R5 initializers)
  → close managed Hindsight runtime
  → release service process lease
  → report shutdown complete
```

### Implementation

- Consolidate normal shutdown, failed-startup cleanup and cleanup-before-restart into one dependency-aware routine.
- On service close failure, retain the service, managed runtime and process lease. Do not continue releasing prerequisites.
- Preserve the original startup exception while separately recording cleanup failure; never replace retained fields with new instances.
- Startup must fail cleanly if earlier cleanup is still incomplete. Recreate an executor only after the previous lifecycle is fully closed.
- Stop accepting new requests before draining the executor; do not close the service while an accepted HTTP handler can still call it.
- Make every worker's close result truthful: a bounded join with a still-live thread must report incomplete close. Request stop on independent workers first; join dependencies in order.
- On a failed startup constructor, ensure retained resources remain reachable for retry by their owning layer; do not let an exception abandon the only handle to a live writer.
- Emit `lifespan.shutdown.failed` whenever required resources remain owned. Repeated cleanup attempts may eventually emit complete after all dependencies drain.
- A host may terminate the process after shutdown failure; process exit releases OS locks. Do not voluntarily hand ownership to another service while the old process remains active.

### Tests and acceptance

- Real ASGI lifespan callbacks with service close failure: failed message, retained runtime, held service lease.
- Runtime close failure: retain runtime and lease; service must not be recreated.
- Startup after incomplete cleanup is rejected without overwriting handles.
- Partial construction failure after a writer starts retains a retryable owner.
- Active HTTP request during shutdown finishes before its service resources are closed.
- Source/workflow worker outlives join budget: shutdown remains incomplete.
- Second close succeeds after gates release; third close is harmless.
- Combine with R5's delayed initializer and verify both indexing and service ownership.

## 7. Define source catch-up independently from page arrival — R6

Files: `personal_memory/source_sdk.py`, `source_sync.py`, `source_runtime.py`, adapter contract documentation and source coverage tests.

### Design and compatibility

Keep existing page fields and defaults. Define the effective outcome centrally:

```text
page_committed = successful commit/receipt result
checkpoint_complete = committed result.page_complete
caught_up = page_committed AND checkpoint_complete AND NOT page.more
```

- `complete` describes whether the page checkpoint may advance; `more` describes additional catch-up after that completed checkpoint. `more=False` cannot override an incomplete checkpoint.
- Accept legacy pages that omit `more`; their existing default remains false, but they still require `complete=True` to count as caught up.
- Accept incomplete pages with `more=False` conservatively as not caught up rather than introducing a breaking validation rejection.
- Derive the worker outcome from the committed receipt, including replay, rather than treating a returned adapter object alone as proof of checkpoint success.
- Runtime scheduling and signal acknowledgment must use the same normalized outcome, preferably an additive worker result such as `caught_up`.
- Preserve the captured signal high-water mark. Signals arriving during a pass remain pending.
- Continue completed-but-paging feeds promptly. Incomplete/no-progress pages need a bounded retry delay or existing backoff mechanism so a retained signal cannot cause a tight polling loop.
- Keep authentication parks, source pauses, backoff and per-partition coverage intact.
- Do not alter page receipt digests merely to add scheduling metadata; preserve replay compatibility.

### Tests and acceptance

- Empty and nonempty incomplete pages retain signals and do not advance checkpoints.
- Missing `more` with incomplete and complete pages follows the compatibility rule.
- Complete page with `more=True` retains signals; complete final page acknowledges them.
- One incomplete partition prevents acknowledgment for the whole connection.
- Same result with either stream ordering, a backoff feed, or a failed feed.
- New signal during a pass survives acknowledgment of the captured high-water mark.
- Replaying an incomplete receipt does not convert it into completion.
- Repeated incomplete pages do not spin; a later valid completed page can recover using valid receipt identity.
- Gmail historical/live fixtures and a non-Gmail adapter use the same core outcome.

## 8. Integrated validation and release gates

### Cross-boundary scenarios

1. Fresh service, empty semantic archive, source connection, first imported mail, semantic candidate retrieval and awareness packet preparation.
2. Historical import plus live arrivals; interrupt indexing, change models and restart; verify source checkpoints, per-model vectors and awareness state remain consistent.
3. Ingest → persist vectors → fail accelerator publication → retire evidence → retry; no current recall or derived artifact may resurrect the retired record.
4. Delay model construction while shutting down a service receiving source work; a replacement process cannot acquire ownership early.
5. Upgrade an archive containing A/B vectors, old backlog, backoff rows, retired records and the already-lost A obligation; reconcile once, reopen cheaply and recover candidates.
6. Source partial-page retry and a foreground Hermes turn: Hermes must not be told processing is caught up before checkpoint completion.

### Commands/checks

- Run targeted suites for each stage with injected embedders and controlled failures.
- Run the complete unit suite with the real pinned Hermes provider contract and scoped model-disable settings. All deterministic tests must pass; document any optional skips explicitly.
- Run concurrency/publication suites repeatedly with event-controlled races, not timing guesses.
- Run the real Uvicorn lifecycle/authentication integration and pinned Hermes release smoke using synthetic data.
- Check the existing Hermes host patch remains applied and unchanged.
- Run a real embedding/HNSW smoke if dependencies are available; label live model tests separately from deterministic correctness tests.
- Test supported legacy schema upgrades and restart after injected migration interruption.
- Check large-archive idle polls and active-model switches for accidental full scans. Measure before/after SQL count, embedding requests, backlog drain throughput and live-arrival delay; do not trade correctness for a throughput target.

### Completion criteria

- Every R1–R7 reproduction becomes a permanent passing regression test.
- Full suite has no unexplained failures; the previous four prefetch failures disappear.
- No required obligation is silently lost across model switches, crashes or retirement races.
- Shutdown never reports success while owned work can still access released dependencies.
- Current retrieval never exposes retired/deleted evidence; explicit historical behavior remains unchanged.
- Existing source adapters and Hermes tools retain their public contracts.
- No repeated archive reconciliation on ordinary idle polls or healthy reopen.
- README/operations and source-adapter docs describe new lifecycle, completion and migration behavior accurately.

## 9. Upgrade and rollback handling

- Take a verified backup before deploying the internal semantic schema migration; stop the old writer before starting the new one.
- Apply migration under exclusive service ownership, preserve canonical records and vector data, and expose incomplete reconciliation through readiness.
- An interrupted migration/reconciliation must resume or roll back transactionally; it must never announce readiness based on old activation watermarks.
- Do not promise that an older binary understands the new work tables. Document rollback via a verified pre-upgrade backup or an explicit reverse migration; account for data ingested after upgrade before restoring any backup.
- Keep public wire/API compatibility distinct from unsupported mixed-version concurrent writers.

## Deferred performance work

The review's Hindsight queue optimization, cross-record embedding batches, larger consolidation batches and combined freshness/awareness requests are useful follow-ups. They are not required to fix R1–R7 and should be measured and reviewed separately after these invariants are covered. This avoids enlarging a correctness migration with unrelated inference and scheduling changes.
